# Learn from recruiting feedback

## Read the feedback

- Fetch current private feedback and comments with the person, role/version and prior assessment.
- Keep the literal choice and explanation separate. Record the known author; a property named for someone does not prove they supplied it.
- Blank notes are not rejection. Substantive recorded feedback overrides a stale Pending label. Do not ask for decisions already supplied.
- Distinguish an evidence error, attention preference, fit disagreement and feasibility concern. A label alone can route attention but cannot explain a causal preference.
- Keep feedback role-specific. Do not transfer MTS judgments into internship labels.

## Change only what is supported

- When Lina requests skill improvements, make the narrow supported procedural edit and validate it. Otherwise propose the change.
- Preserve counterexamples and disagreements. School prestige, missing public code and feasibility concerns must not silently become ability judgments.
- Do not change weights or activate faster ranking through maintenance. For active-criteria changes, follow the review and approval boundaries in [the decision tree](../../decision-trees.md).
- Freeze guidance and split examples by person before evaluation. Seen examples are procedure checks; use fresh people and independent human labels for accuracy claims.
- Report sample size, coverage, disagreements and missing labels. Passing skill validation or code tests does not prove better hiring judgment.
- For MTS-specific hypotheses read [calibration notes](../../decision-trees.md); do not treat them as universal rules.

Return the observed feedback, supported change, counterexample and verification limit. Keep names and literal comments in private Notion.
